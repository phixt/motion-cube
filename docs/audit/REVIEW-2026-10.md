### P1-2 `playFrames({loop:true})` 根本不循环 **[已复现]**
`src/hand/handApi.ts:106-124`


## 四、P2 —— 技术债（不阻塞，但应排期）

### 求解器
- **求解全程在主线程同步执行**：`prepareSolvers()` 预热约 560ms（实测），搜索尾部单次

- `zbl.ts` 头注释「任意棱已定向的顶层态都恰有一条 ZBLL 一步解」实测**假**（命中率 50%）。
- `cfop.solveSlot` 的 `EJECT[4]` 兜底分支不可达（0/2436），且语义写错（弹的是角不是棱）。

### 渲染线
- `CubePlayer.dispose()` **全仓无调用点**（游戏页 / 编辑器都不释放 cubing 播放器与场景）。
- 灰面板注册 window 级 `pointerup` 监听且从不移除，面板也没有销毁接口。
- `GrayOverlay.init()` 无重试：3D 场景未就绪时标灰**永久静默失效**。

- 标灰面板小魔方「默认转了 U」：面板忠实画实时态，而默认起始态是公式逆序态（todo 已知）。
- render 后端（休眠中）尚有 5 处会坏：`setMoves` 重上色 22/54 错色、播中改速瞬移/倒退
  （63.3°→86.7°→63.4°）、300ms/步 与项目 1000ms 基准冲突、`setState` 永久切到
  state 材质模式、`play()` 在当前态上重播。
- `RenderCubeHost` 自动自转慢了 1000 倍（参考实现用 ms，这里 dt 是秒）。

### 手部
- `HandRigView` **没有 `dispose()`**：每次编辑器挂载/卸载与每次 `buildRig()` 重建都泄漏
  three.js 几何与材质。
- `HandRigView.applyPose()` 每次姿态变化都 `new SphereGeometry + new MeshBasicMaterial`
  （第 176-177 行）且**从不 dispose**，带 `contacts` 的姿态会无界增长 GPU 缓冲。
- `HandCalibView.dispose()` 调的是 `rebuild()`（重建整只手）而不是 `rebuild(null)`——
  白白重建一次，且新几何从未释放。
- `shape.web` 是**死参数**：被规范化、被持久化、标定页还给了滑条，但几何从不消费。
- 拇指 IP 关节组是空的 → 编辑器的「IP 弯曲」滑条**完全没有视觉效果**。
- `normalizeHandRigConfig` 接受退化指根基准 → 产出 NaN 顶点 → NaN 整个手部包围盒 →
  标定页相机拟合失效。
- `Default shape.facets = 15`（奇数）使环采样不对称，左右手不是严格镜像（thenar 差 0.0087）。
- `clampBend` / `JointDef.range` 从未在渲染时应用，超范围弯曲既不夹紧也不拒绝。

## 五、已证伪 / 降级的报告项

### 证伪：Roux block-2 深度上限 14 导致约 0.2% 的合法魔方求解失败 **[首轮标为 CRITICAL，实测不成立]**

首轮报告称 `roux.ts:150/211/259` 的 `runItem(T.block2, 14, 8e6)` 会因深度上限而
「second block failed」，并给出 0.15%（3/2000）的失效率。**主审复核后无法复现**：

| 验证 | 规模 | 结果 |
|---|---|---|
| 完整求解（纯面步打乱） | 2500 打乱 × 3 方法 = 7500 次 | 失败 0 |
| 完整求解（**项目自己的** `randomScramble(20)`，含宽层/切层） | 1500 打乱 × 5 方法 = 7500 次 | 失败 0 |
| 直接打 block-2 子问题 | 3000 态 | 深度 14 失败 **0**，最大用 1387 节点 |
| 直接打 block-2 子问题 | 20000 态（项目打乱分布） | 深度 14 失败 **0**，最大用 **1614** 节点（预算 8e6） |

深度 14 的搜索节点用量上限只有 1614，距 8e6 预算差三个数量级——**深度上限不是约束**。
合计 **38000+ 次求解、零失败**，与 0.15% 的失效率不符。

**处理**：降级为「低」，仅保留一条加固建议——深度上限只比实测最优解多 1 步
（block2 上限 14 vs 实测最优 13；eo 上限 12 vs 11），余量偏薄，建议提到 16
（实测 0 额外开销，因为失败搜索 624 节点就终止），并给 smoke 脚本补 ≥2000 随机打乱的
回归样本。**不建议**按首轮报告的严重度处理。
